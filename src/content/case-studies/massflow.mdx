MassFlow is a config-first, vendor-agnostic Python toolkit for tandem mass spectrometry (MS/MS) annotation — spectral similarity scoring, version-controlled spectral libraries, and interactive molecular networking. It is not an instrument driver and not a GUI: it is the analytical workflow itself, packaged as software. This case study traces where that workflow came from — five years of postdoctoral research processing high-dimensional LC-TWIMS-HRMS datasets to resolve the real-time self-assembly of polyoxometalate (POM) nanomaterials — and why the failure mode of that research was never the instrumentation, but the annotation layer around it.

## The Analytical Problem

Polyoxometalate self-assembly is a problem of isomerism in motion. A handful of building blocks recombine into 1D chains, rings, and compact spheres, and the mechanism — which cluster forms first, which converts into which — is encoded in the spectra of intermediate species that exist for minutes at a time. Resolving it demands assigning a chemical identity to every species at every timepoint, across a high-dimensional dataset: retention time × drift time × m/z × intensity, with each cluster present in multiple charge states.

The instruments were never the bottleneck. The bottleneck was annotation. Interpreting the data meant matching experimental spectra against reference spectra and tracking assignments across an entire time series — work that lived in vendor software with closed scoring functions, and in one-off Python scripts that were correct once and comprehensible to no one. Spectral libraries were assembled by pointing and clicking inside instrument GUIs, then lost when the computer changed. The analytical result — a mechanism, a publication — depended on the analyst's memory as much as on the data.

## Context & Constraints

The work happened at the University of Glasgow (2017 – 2020) on an automated synthetic-analytical platform: inline microfluidic synthesis coupled directly to electrospray ionization, travelling-wave ion mobility, and time-of-flight mass spectrometry. The platform's purpose was to watch chemistry in real time — no fraction collection, no offline workup, no sample preparation between reaction and analysis.

Four constraints shaped everything that followed:

- **Vendor lock-in.** Raw data arrived in proprietary formats, and the vendor's processing software controlled the scoring, the peak-picking, and the library format. Anything the vendor's GUI could not express required a workaround, and anything it could express was not exportable.
- **Instrument heterogeneity.** The toolkit that resolved POM speciation on a TWIMS-QTOF had to survive contact with Orbitraps, QqQs, and later ICP-MS work. A workflow bound to one vendor's abstractions would die with the instrument.
- **Evidence standards.** The assignments fed peer-reviewed publications — real-time monitoring of a catalytic amination, and isomer-selective POM cluster synthesis. Every annotation step had to be defensible months later, against reviewers' questions.
- **Single maintainer.** The researcher writing the scripts was also the only person who would ever run them. Code that could not be understood after a six-month hiatus was technical debt, not infrastructure.

## The Hardware/Chemistry Solution

The chemistry was solved instrumentally. TWIMS separated isomeric clusters by shape — chains drift differently from rings, rings from spheres — so the morphological story appeared directly in the drift-time dimension. Electrospray preserved solution-phase speciation well enough to observe the earliest intermediates, and real-time sampling caught the chain-to-ring-to-sphere transitions as they happened. The amination-monitoring work went further and followed a catalytic reaction step by step, intermediate by intermediate.

But the instruments could only produce the data. The vendor software could extract peaks; it could not track a chain → ring → sphere transition across a time series, or propagate an assignment from one timepoint to the next. The hardware/chemistry resolution was therefore a decoupling: export data to open formats at the source, and move the analytical reasoning — the scoring, the library, the networking — into code that was instrument-agnostic. The instrument became swappable; the analysis became the asset.

## The Computational Architecture

MassFlow is that decoupling, generalized and packaged. Its architecture is organized around one principle: *everything is a file, and every file is versionable.*

- **Config-first pipelines.** A run is declared in plain-text configuration — inputs, filters, scoring parameters — and committed to Git alongside the data. The same command reproduces the same annotation on any machine, which is what "reproducible" means in practice: the analysis is a file you can diff, not a sequence of clicks you remember.
- **Vendor-agnostic ingestion.** Data enters through open formats (mzML/MGF via pyteomics), so the pipeline does not care whether the acquisition was TWIMS-QTOF, Orbitrap, or QqQ.
- **Transparent spectral similarity scoring.** The similarity function is custom and its parameters are explicit — no closed black box deciding which spectra match. Scores are deterministic and inspectable.
- **Version-controlled spectral libraries.** Libraries are plain-text artifacts managed by Git: additions are diffs, regressions are visible in review, and a library's provenance is its commit history.
- **Molecular networking as output, not afterthought.** Annotated spectra link into interactive networks that can be explored in the browser — the same kind of view that made POM speciation legible, now available for any dataset.
- **CLI-first, tested, CI-guarded.** A documented command-line interface and a Python API, with tests run on every change. The postdoc's one-off scripts became the toolkit's first regression tests: the workflow that resolved POM self-assembly is now permanently executable.

## Outcome & Impact

The measurable outcome is a change in what the workflow *is*. The Glasgow analysis — previously scripts on a bench machine, entangled with one vendor's software — now runs as a documented, MIT-licensed, open-source pipeline that anyone can install, review, and reproduce. Spectral libraries that would once have been lost to a hardware refresh are now version-controlled artifacts with a reviewable history.

The liberation from vendor lock-in is the point. A laboratory that adopts MassFlow can change instruments — or vendors — without abandoning its libraries, its scoring, or its analysis history. The annotation layer finally outlives the instrument software, and the data outlives both.

The single-maintainer constraint turned out to be a design virtue: because one person had to understand everything six months later, the toolkit is plain files, explicit configuration, and no hidden state — built for the long haul, by design. The same philosophy now extends outward: [MSMCP](https://github.com/janusson/MSMCP) exposes mass spectrometry datasets as queryable tools for AI agents, keeping the data open and reachable at the next layer up.

MassFlow is the answer to a question the postdoc never asked directly: *what would it take for another chemist to reproduce my annotation from raw data alone?* The answer turned out to be a toolkit. It lives today at [github.com/janusson/MassFlow](https://github.com/janusson/MassFlow), with documentation at [ericjanusson.ca/MassFlow](https://ericjanusson.ca/MassFlow/).
